## 第一轮已确认

1. Discovery 的目标是发现值得进一步研究的主题。例如输入 AI Trending，得到某机构发布新模型这样的具体事项。用户举的“OpenAI 发布 GPT-6”在本设计中仅作示例，不是经本项目验证的新闻事实。
2. CLI 负责采集、证据处理、状态和校验；宿主 Agent 负责语义判断与综合。用户要求引入 Jev 辅助判断；第二轮已确定由 CLI 调用、保留分维度判断、Agent 最终选择。
3. 当时首版仅实现 Discovery 所需的最小主题研究核心，预留 Named-Topic / Comparable；第八轮已将直接 Named-Topic 研究纳入首版，Comparable 仍预留。
4. Digg 目标明确为 https://digg.com 。
5. 沿用初始范围：Skills + CLI；CLI 内提供 Agent 操作指南；目标渠道为 X、Reddit、GitHub、Hacker News、Digg、arXiv、Web search（Brave）。

术语见 [CONTEXT.md](../../CONTEXT.md)，分工决策见 [ADR 0001](../adr/0001-agent-cli-responsibilities.md)，上游参考分析见 [阅读记录](../research/last30days-workflow.md)。

## 本轮新增事实核查（2026-09-28）

### Jev

TypeSafe 官方文档将 Jev 定义为对给定状态执行结构化判断的模型。支持 Choice（分类选择）、Score（按标准评分）和 Noul（是非概率），而非生成自由文本。官方建议将复杂评价拆成单一维度的问题，再由程序组合结果。

因此，领域相关性、是否包含具体新进展、证据是否支持某项陈述等是可以讨论的辅助判断维度；将它们作为实际接入范围仍需确认。不得把模型置信度当作新闻已被证实的概率。

来源：[官方介绍](https://docs.typesafe.ai/introduction)、[官方快速开始](https://docs.typesafe.ai/introduction/quickstart)。未调用模型，也未测试账号可用性或判断效果。

### Digg

官网 `llms.txt` 明确说明 `di.gg` 是保留别名，并声称旧 `/ai` 跳转到 `/tech`。当前官网公开免认证 JSON/YAML 发现数据，包括当前主题簇、排名主题簇以及上升主题簇；文档建议排名数据读取 `position` 字段。

这修正了上一轮可能让人误以为 digg.com 与 di.gg 是独立产品的表述。接入应以当前 digg.com 文档为准；与直接 X 采集的证据关系仍需要去重和溯源。

匿名只读实测：`ai-clusters-ranked.json` 和 `ai-rising-clusters.yaml` 返回 HTTP 200。但运行态与说明存在差异：JSON 中仍出现 `/ai/{short_id}` URL，首页已有科技之外的分类导航；不能仅凭 `llms.txt` 判断全部领域覆盖或跳转行为。首版可用的稳定字段与跨分类覆盖仍需更完整验证。

本次排名数据样本生成时间为 `2026-09-28T09:51:00.000Z`；虽有 10m / 1h / 6h 互动增量字段，其状态为 `unavailable_not_backfilled`，不能把缺失数据解释为零增长或已测得增速。Rising 返回了 40 个主题簇，而说明描述为排除 top 20；该列表不能按数组顺序直接解释为热度排序。

来源：[机器可读入口说明](https://digg.com/llms.txt)、[官网介绍](https://digg.com/about)、[排名数据](https://digg.com/ai-clusters-ranked.json)、[上升主题数据](https://digg.com/ai-rising-clusters.yaml)。尚未验证所有端点，也没有确认通用搜索 API 或 RSS 契约。

| 新探索 | 研究 Jev + browser_use 是否适合作为数据获取兜底 |

浏览器兜底目前是探索请求，不等于已批准新增必需依赖或任意浏览器 Agent。需区分浏览器渲染、有限动作选择、通用生成式 Agent 与原有候选价值审阅；研究记录见 [浏览器兜底探索](browser-fallback.md)。

## 第二十轮：移除 MVP 额度控制

用户明确要求 MVP 删除额度概念，无需控制额度。撤回采集次数上限、Jev 费用上限、默认额度、预算耗尽停机及额度恢复设计；Q61–Q63 不再需要回答。早期 Q14 / Q41 / Q43 / Q45 / Q46 / Q56 中用于额度管理的规则不再是 MVP 执行约束。

| Q64：Named-Topic 渠道覆盖 | 默认尝试全部已配置渠道 |

Named-Topic 与 Discovery 的默认覆盖一致，不采用由 Agent 按相关性默认缩减渠道的建议。Agent 仍生成各渠道的查询计划，CLI 校验并执行；渠道失败允许按既有规则通过 Brave 兜底并标记缺失。默认尝试不等于要求每个渠道都有结果，也不等于未配置渠道必须发起请求。既有结果复用与显式刷新规则继续适用。
